# Multi-machine crew dispatch

Design for spreading the crew's work over several machines without the commander placing it.
Status: **stage 1 is built** (`chartroom nodes`, `chartroom node probe`, `chartroom node init`:
read-only discovery plus each node's own budgets); stages 2 to 4 are designed here and not yet
built. "desk" and "mini" below are example labels: an always-on desktop that holds the home of
record, and a laptop used headlessly.

**Devices push to the brain** (the commander's direction, superseding the ssh protocol below where
they differ): each machine runs chartroom's device agent, keeps the one connection, outbound, and
the brain never reaches out to it, holds no key to it, and asks it to open no port.
[§12](#12-devices-the-brain-never-reaches-out) describes what is built of that: enrolment, the
device's own revocable token, heartbeats that Fleet and `chartroom nodes` read, commands over
the connection, and pinned dispatch: a task pinned to a device runs there. Automatic placement is
not built yet.

## 1. Goals and shape

The commander uses one XO in one **home of record**: an always-on desktop (the "desk"). They reach it from whichever
laptop they are on. Workers should spread over every machine that has room, without the commander placing them.

- **Origin.** The home that created the task. It is the only record: `meta.json`, `brief.md`, `events.log`, report,
  plan and artifacts. There is one origin per task, forever.
- **Node.** Any machine that runs workers. It has a chartroom install and a node config, and **no home and no XO**. The
  origin's own machine is a node too (the "local node"), so placement weighs it like any other.
- **Dispatcher.** The chartroom process that places a task. Today that is always the origin. Any chartroom may
  dispatch onto the network: nothing assumes a single dispatcher.
- **No master for capacity.** Each node grants or refuses a slot itself, atomically, under a lock on the node.
- **No new daemon.** The node runs nothing of its own. Everything is an ssh call from the dispatcher, plus the one
  long-lived event stream per node that the origin's `watch` already owns. The worker runs in the node's own
  login-session runner (hc or herdr), as it does locally.

```
  laptop ──ssh/herdr/dashboard──▶ desk: origin home + XO + watch
                                     │  ssh -o BatchMode=yes (fixed verbs only)
                    ┌────────────────┼─────────────────────────┐
                    ▼                ▼                         ▼
             local node        node "mini"                node "laptop"
             (as today)        spool: leases, guests      spool: ...
                               worktree + hc terminal     (budget 30%, pause on battery)
                    events ◀── one `node stream` per node (origin's watch) ──┘
                    commits ◀── git fetch over ssh (git-upload-pack, read-only)
```

## 2. Where each file lives

| Thing | Origin home (record) | Node |
|---|---|---|
| `meta.json` | the record; gains `node`, `node_target`, `node_spool`, `lease`, `node_off` (bytes of the node log already copied) | `guests/<origin-key>/tasks/<id>/meta.json`: a guest record (`guest: {origin_key, origin_machine, origin_home, lease}`) plus the runner's handles (hc terminal, session id) |
| `brief.md` | the record, with origin paths | a **rendered copy**: the protocol's task-dir paths, `CHARTROOM_HOME=` and helper path rewritten to the node's spool and binary (exact-prefix substitution of what `write_brief` generated) |
| `events.log` | the record: node lines appended **verbatim** in node order, plus the origin's own notes | the worker's hooks and `chartroom event` append here (node-local, so nothing crosses machines at write time) |
| `report.md`, `plan.md`, `final.md`, artifacts | **pulled copies**, authoritative once pulled (on every wake-worthy event and at close) | written by the worker |
| `inbox.md` (task) | the XO writes it | **pushed** on `steer --inbox` |
| `node.json` (new) | cached remote liveness: `{live, at, contact, error}`, written by the watch's stream | n/a |
| `claude-settings.json`, launcher, `hooks.log`, `pane.log` | n/a | generated by the node's own `dispatch`, with node paths |
| worktree + branch | n/a (fetched back as a branch) | under the node's checkout (`.worktrees/`) or `spool/worktrees/<repo>/<id>` |
| leases, slot lock | n/a | `spool/leases/`, `spool/.slots.lock` |
| budgets | n/a | `~/.config/chartroom/node` |

- **The spool** is `${XDG_STATE_HOME:-~/.local/state}/chartroom/node/`.
- **A guest directory** `guests/<origin-key>/` is a minimal chartroom home: `tasks/` only, no `AGENTS.md`, never in the
  node's `homes` list. That is why `status --all-homes` and the radar on the node never show guests twice.
  `<origin-key>` is `<origin machine label>.<home name>`.
- **Unchanged code on the node.** The node runs ordinary `chartroom dispatch`, `peek`, `steer`, `park` and `close` with
  `CHARTROOM_HOME` set to the guest directory. Every backend, hook, trust-dialog handler and park path works there
  unchanged.

## 3. The node protocol

Every call is `ssh -o BatchMode=yes -o ConnectTimeout=5 -o ServerAlive* <target> '<fixed command>'`, with connection
reuse (`radar_ssh`). Labels and ids are validated by regex before they reach a shell. Brief text, meta and steer
messages go on **stdin as JSON**, never interpolated into the shell line. Remote PATH comes first from
`CHARTROOM_RADAR_REMOTE_PATH`.

| Verb (on the node) | R/M | Stage | What it does |
|---|---|---|---|
| `bash -s` < `lib/nodeprobe.sh` | **R** | 1 | Agentless probe. Prints `key<TAB>value` lines (`probe_schema 1`): capacity, CPU and memory in use (`cpu_use`, `mem_used_pct`), power, HID idle, budgets if the node is initialised, tools and logins checked functionally (section 6), each agent (`agent`: a worker by its task, an XO by its home, any other by its directory's name and its tab; no title, message or path), project checkouts. Needs nothing installed; bash 3.2-safe; starts no hc core |
| `chartroom node probe [--json]` | **R** | 1 | The same script, run by an installed chartroom, plus its leases and guests (stage 3) |
| `chartroom node lease --origin K --task ID --cost CPU,MEM --ttl S` | **M** | 2 | Under the slot lock: re-checks budgets, then grants a `reserved` lease or refuses with numbers (JSON) |
| `chartroom node release --origin K --task ID` | **M** | 2 | Drops a lease (idempotent) |
| `chartroom node accept --origin K` (stdin: task bundle) | **M** | 2 | Idempotent by (origin, task, lease). Creates the guest; `git fetch` in the node's checkout; checks `base_sha`; creates the worktree; runs `dispatch` on a login-session runner; turns the lease `held`. Prints `{worktree, backend, handles}` |
| `chartroom node stream --origin K --from ID:OFF,...` | **R**, plus lease renewal | 2 | Long-lived. JSON lines: `hello` (node clock, version, protocol), `line` (id, offset, text), `live`, `file` (a report/plan/artifact changed), a heartbeat every 30 s. Renews K's held leases while it runs |
| `chartroom node tick --origin K` | **M** (node-local housekeeping) | 2 | Called by the stream every 30 s. Expires stale reservations, runs the node-side backend watch for K's guests (the `agent: awaiting-input` lines it logs), and `park --due` for K's guests |
| `chartroom node file --origin K ID NAME` | **R** | 2 | Cats brief/report/plan/final/events/an artifact of a guest |
| `chartroom node peek --origin K ID N` | **R** | 2 | The guest's `chartroom peek` |
| `chartroom node steer\|stop\|park --origin K ID` (message on stdin) | **M** | 2 | The guest's own verb |
| `chartroom node attach --origin K ID` (`ssh -t`) | **M** (may resume a parked worker) | 2 | `chartroom attach` on the node |
| `chartroom node close --origin K ID [--discard]` | **M** | 2 | Refuses a dirty worktree, as today; removes it; releases the lease |
| `git-upload-pack '<guest worktree>'` (via `git fetch <target>:<path> <branch>`) | **R** | 2 | Commits come back to the origin as a branch. Nothing pushes into a node |

- **Optional hardening: a forced-command key.** A dedicated key in the node's `authorized_keys` with
  `command="chartroom node gate",no-pty,no-port-forwarding`. The gate reads `SSH_ORIGINAL_COMMAND` and runs only the
  verbs above, plus `git-upload-pack` of a path under the spool or a guest worktree. `ssh -t` attach would need a
  second, interactive key. Without the gate, the dispatcher's key is as strong as the commander's own login.

## 4. Slots, leases and locks

- **The lock** covers only the critical section of `lease`. It is an atomic `ln -s <pid> spool/.slots.lock`, the same
  idiom as `task_lock`. Its holder is the `chartroom node lease` process on the node, which lives only for the call, so
  taking over a lock whose holder pid is dead is correct here. Wait at most 10 s, then refuse "node busy".
- **A lease** is a record, not a lock: `spool/leases/<origin-key>.<id>.json` =
  `{origin, task, state, granted, expires, cost}`. **Every time in it is the node's clock**, so clock skew between
  machines never affects a lease.
  - `reserved`: granted, waiting for `accept`. TTL `CHARTROOM_NODE_RESERVE_SECONDS` (120). It lapses if no accept comes.
    Lapsing is lazy: the next lock holder or `tick` drops it.
  - `held`: set at accept. Renewed by the origin's stream/tick. Expires after `CHARTROOM_NODE_LEASE_MINUTES` (15)
    without renewal.
- **Expiry never kills or frees a live worker.** A `held` lease that expires because the dispatcher disappeared becomes
  `orphaned`.
  - Its worker keeps running, keeps its worktree, and still parks when idle (the node's `tick` runs whenever any
    origin is connected).
  - The slot stays counted while the worker is live: resource truth beats bookkeeping.
  - The next stream from that origin re-adopts the lease.
  - Expiry frees **only reservations that never became a live worker**.
- **Counting slots** (under the lock):
  - every live worker on the node, from all its own homes and all guests, not parked;
  - plus unexpired reservations.

  The node counts its own homes' workers too: the desk runs its own crew and is a node at the same time.
- **Two dispatchers.** Both may read the same probe and both may pick `mini`. The first `lease` under the lock gets the
  slot. The second gets a refusal with fresh numbers and re-places: at most 3 tries, then it queues (stage 3).
- **Name collisions.** hc and herdr terminal names are task ids. `lease` refuses an id that any origin already holds on
  that node, and `hc_clear_stale` already refuses a live terminal of the same name. Ids are `slug-hex4`, so this is
  rare and loud, never silent.
- **Retries.** A connection failure does not prove a mutation did not happen. `lease` and `accept` are idempotent by
  (origin, task), so a retry returns the existing lease or guest.

## 5. Placement

**Inputs.** For each node `n`, taken from a fresh probe (≤ 30 s old):

| Symbol | Meaning |
|---|---|
| `C` | logical cores |
| `B` | cpu budget (0–1] |
| `W` | max workers |
| `M` | memory budget (0–1] |
| `R` | RAM |
| `L` | 1-minute load average |
| `F` | free memory fraction (macOS `kern.memorystatus_level`) |
| `w` | live crew workers: the node's hc terminals carrying `chartroom.task` (from the first frame of `hc events --json`, which carries labels; `hc ls` does not). An XO or a person's own agent is not a slot, though its load counts through `L` and `F`. An hc with no event stream falls back to every live agent |
| `r` | reservations younger than 180 s (the node's own, plus the dispatcher's in-flight placements) |

A worker's cost is `c` = `CHARTROOM_WORKER_CPU` (default 1.5 cores) and `m` = `CHARTROOM_WORKER_MEM_GB` (default 1.5;
an idle Claude worker measured 1.06–1.11 GB in the park work).

**Projected utilisation if this task lands on n:**

```
u_slots = (w + r + 1) / W
u_cpu   = (L + c·(r + 1)) / (C · B)
u_mem   = ((1 − F)·R + m·(r + 1)) / (R · M)
U(n)    = max(u_slots, u_cpu, u_mem)
```

**Steps:**

1. **Hard filter** (section 6). Drop nodes that cannot run the task, are paused (on battery with `pause`, not accepting, or
   in stage 4 the commander is at its keyboard), or have `U(n) > 1`. If nothing is left, the task is `queued`
   (stage 3), or with `--machine` it fails with the numbers.
2. **spread (default).** Take the lowest `U`. Nodes within **0.10** of it form a tie group, ranked by:
   - locality: +2 the checkout already has `base_sha`; +1 recent `FETCH_HEAD` and installed deps
     (`node_modules`, vendor/bundle); +1 the images the task needs are cached (stage 4); +1 the dispatcher's own machine;
   - then lower `U`;
   - then the label, so the choice is deterministic.
3. **pack** (`CHARTROOM_PLACEMENT=pack`). Take the highest `U ≤ 1`: fill one node first. Ties use the same locality
   ranking.
4. **local** (`CHARTROOM_PLACEMENT=local`). Turns placement off: everything runs here, as today.

Each node is measured against **its own** budget, so spreading evens out the *fractions*. A node with twice the
capacity takes about twice the tasks. Reservations count at full cost for 180 s, because `load1` is an exponentially
weighted average that reaches about 95% of a step after 3 minutes. Without that, a burst of five dispatches would all
see the same idle node.

**Worked example** (c = 1.5, no slot or memory pressure):

| Node | Capacity C·B | Load L | 1st task u_cpu | 2nd task |
|---|---|---|---|---|
| desk | 28 × 0.8 = 22.4 | 6 | (6 + 1.5) / 22.4 = 0.33 | 0.33 → **here** |
| mini | 16 × 1.0 = 16 | 3 | (3 + 1.5) / 16 = 0.28 → **here** | (3 + 3) / 16 = 0.375 |

Total usage climbs evenly instead of filling one machine to 100% first.

**Never moved.** A running task never migrates. `steer`, `peek`, `attach`, `park`/resume and `close` always go to its
node.

**On macOS, budgets are admission control, not caps.** There are no cgroups. The limits work in two ways:

1. **Admission:** no new worker starts once `U` would exceed 1.
2. **Priority:** the node's launcher prefix, set by `CHARTROOM_NODE_PRIORITY`:
   - `normal`;
   - `nice` (`nice -n 10`, the default);
   - `background` (`taskpolicy -b`). This throttles CPU and I/O, and on Apple silicon keeps the worker on the
     efficiency cores. That suits a laptop in use and badly hurts a headless node.

A running worker's builds can still push a node past its budget. Stage 4 yields (lower priority, park idle workers,
stop placing there). It never kills a worker.

## 6. Hard requirements (filter before scoring)

- **What a task needs:**
  - its agent, present **and logged in**;
  - `git`;
  - a checkout of its project, matched by canonical remote: `host/owner/repo`, lowercased, scheme, user and `.git`
    stripped, so `git@host:o/r.git` ≡ `https://host/o/r`;
  - its `base_sha` reachable from that remote. The origin checks with `git branch -r --contains`. A base that exists
    only locally keeps the task on the origin;
  - anything in `new --needs go,docker,ruby,node,gh` (stage 3), and optionally per project in `projects.md`.
- **Capabilities are functional, checked in the worker's context:**
  - `claude auth status` → `loggedIn`; `codex login status`; `gh auth status` exit 0; `docker info` (daemon up, not
    only the binary); `go version`, `ruby -v`, `node -v`; bash ≥ 4.
  - These run **through the node's login-session runner core** (`hc exec`), only after its socket answers (a probe
    never starts a core).
  - With no core answering, logins read `unknown` over ssh. For the filter, unknown means no, because an ssh
    shell cannot see a Mac's keychain. A probe run locally outside ssh (`chartroom node probe` in a terminal of the
    login session) checks them directly.
- **Checkouts** are git repos at most 3 levels under the node's `CHARTROOM_NODE_PROJECT_ROOTS`, with their canonical
  remote, path and `FETCH_HEAD` age. A node never clones on its own (that would be a later, opt-in
  `CHARTROOM_NODE_CLONE`).

## 7. Failure modes

| Failure | What happens |
|---|---|
| **Node unreachable mid-task** (sleep, Wi-Fi, reboot) | The stream ends or times out. The task reads `live: unreachable` (its state is unchanged). After `CHARTROOM_NODE_LOST_MINUTES` (10) it wakes once: `lost: node mini unreachable since T (<ssh's message>); its worktree and commits stay on mini; chartroom recover <id>`. It shows as `lost` (the radar's Adrift sector). Nothing is deleted. When contact returns, the stream resumes from `node_off`: events written meanwhile replay in order, and the task carries on (`note: node mini back; N events replayed`) |
| **Worker gone after a node reboot** | Its worktree and commits are on the node. `chartroom recover <id>` (stage 2): (a) **default**, on the same node, resume the recorded session (`claude --resume`, as park's revive does) in the same worktree; (b) `--elsewhere`: fetch the branch to the origin and dispatch a **new** worker on another node from the branch tip, with the brief plus "resume from <branch>; the last worker's last events: …". A dead worker can be replaced. A live one never moves |
| **Commits only on a dead node** | The origin fetches the branch (`git fetch <target>:<worktree> <branch>`) on every wake-worthy event (`decision`, `blocked`, `waiting`, `done`, `failed`), at `close`, and every 30 min while the branch moves. At worst it loses that window, until the node returns |
| **Stale checkout** | `accept` runs `git fetch origin` in the node's checkout before **every** worktree, then `git cat-file -e <base_sha>`. If the sha is missing, accept refuses (`base <sha> is not on the remote; push it or run it locally`) and the lease is released. The node's own checkout is never pulled, reset or switched (a person may be using it): the worktree starts from the sha |
| **ssh auth expiry** (keys, agent, Tailscale SSH re-check) | BatchMode never prompts. Exit 255 with `Permission denied` / `Host key verification failed` / a Tailscale check URL marks the node's contact `auth`. It wakes once per outage: `node mini: ssh needs you (<message>); run ssh mini once in a terminal`. Placement skips the node, and its tasks read `unreachable` |
| **Clock skew in event timestamps** | Node lines keep the node's timestamp (the line format is a stable contract) and the origin's **append order** is the order. The stream's `hello` measures the skew (node epoch − origin epoch − RTT/2); above 30 s it logs `note: node mini's clock is 74 s ahead`. Leases use only the node's clock. Waiting windows use the worker's own until-time, and their 15-minute grace absorbs small skew |
| **Logins locked** (rebooted, not logged in to the GUI, FileVault) | No runner core answers, so logins are `unknown` and the node is not eligible. A worker never starts from the ssh shell |
| **Dispatcher dies between lease and accept** | The reservation lapses after 120 s |
| **Dispatcher dies after accept** | The worker runs on. The lease becomes `orphaned` after 15 min, is still counted while the worker is live, and is re-adopted by that origin's next stream |
| **Node over budget** (its owner starts a big build) | Nothing is pre-empted. New placements go elsewhere. Stage 4 lowers priority and parks idle guests |
| **Accept fails** (disk full, worktree error) | The lease is released, the error is logged on the origin task, and the dispatcher tries the next node |
| **Version skew** | `hello` and the probe carry `probe_schema`/`node_protocol` and the chartroom version. A different protocol major is listed as `incompatible` and never used |

## 8. Security

- **Credentials never move.** The only payloads are the brief, a meta subset and steer messages: no environment,
  tokens or config. Each node uses **its own** claude, codex and gh logins, which the commander makes once per node.
- **The node never connects back.** No node holds credentials for the origin. Events come back over the origin's
  outbound stream, and commits by the origin's `git fetch`.
- **What a dispatcher can run on a node.** The protocol is a fixed set of verbs with validated arguments. The ssh key
  itself is as strong as a shell login unless the node pins it to `chartroom node gate` (section 3). Workers run as the
  node's user with the authority their brief grants, exactly as locally, so a worker on a laptop can read that laptop's
  files. That is why being a node is **opt-in**: a machine without `node init` is never placed on, and
  `CHARTROOM_NODE_ACCEPT=off` stops new work there at once.
- **Data at rest.** Briefs and worktrees land on the node's disk, in the commander's own trust domain.
- **Tailscale is assumed, not required.**
  - All machines are on one tailnet, with MagicDNS names as ssh targets.
  - Tailscale ACLs allow ssh only between the commander's devices, and WireGuard encrypts the hop.
  - No new listening port and no daemon. The dashboard's token rules are unchanged.
  - Tailscale SSH "check" mode shows up as auth expiry (section 7).

## 9. How a remote task is shown

- **`status`.** Rows gain `machine` (`null` when local) and `node_contact`. The table gets a `MACHINE` column **only when
  some open task runs elsewhere**. LIVE comes from the cached `node.json` (`working`, `unreachable 4m`). `status` never
  opens ssh, so it stays fast and works offline.
- **board / dashboard.** Cards carry an "on mini" chip. The task page gets a machine row. Its live pane is the proxied
  `node peek` (bounded at 25 s, like the radar's).
- **radar.** The origin's record is drawn under the node's machine (`m` splits by machine), labelled with its home and
  "from <origin machine>". The node's own `status --all-homes` never lists guests, so a task is never drawn twice.
- **Herdr.** hc workers appear in the node's Herdr app. Where the viewer's hc core links that node (hc's machine link),
  they also appear on the viewer's machine.
- **`chartroom nodes`** (stage 1) is the capacity and capability table.

## 10. Backward compatibility

- **With no node configured, everything is as today.**
  - `new` and `dispatch` do no placement unless at least one remote node answers its probe *initialised* and
    `CHARTROOM_PLACEMENT ≠ local`.
  - `chartroom nodes` lists this machine only.
  - No new process runs.
  - `status`, board and radar output are unchanged.
  - Every new meta key is additive. `meta.json` schema 1, the event line format and the brief protocol do not change.
- **A task without `meta.node` takes exactly today's code paths.** Every remote branch is gated on `meta.node`.
- **An older chartroom on a node** answers the probe (it is agentless) but has no `node` verbs, so it reads `no node
  protocol` and is never placed on.

## 11. Staging

| Stage | Delivers | Mutates other machines? |
|---|---|---|
| **1** (built) | `lib/nodeprobe.sh`, `chartroom node probe`, `chartroom node init` (budgets file, written on the node itself), `chartroom nodes` table | No. The dispatcher only reads |
| **2** | an `install.sh` node mode (an install with no home: today's install runs `chartroom init`, which makes one); `new/dispatch --machine <m>` end to end: lease, accept (fetch + worktree + login-session runner), stream into `watch`, `node.json`, steer, peek, attach, park, close, branch fetch-back, `recover`, `lost` | Yes: the protocol's M verbs |
| **3** | Automatic placement (`spread`/`pack`/`local`), budgets enforced at `lease`, the `queued` state with a drain on capacity, `new --needs` | Yes |
| **4** | Yield while the commander is at the keyboard (HID idle < `CHARTROOM_NODE_IDLE_MINUTES`: stop placing there, `background` priority for running guests), battery pause, cached images in locality, rebalancing the **queue** (never running workers) | Yes |

**Later, not planned:** `chartroom adopt <id>` would let another home take over a task's record by moving its
`origin-key` on the lease and copying the record. The lease and spool keys are shaped for it, but nothing is built.

## 12. Devices: the brain never reaches out

Built: enrolment and heartbeats (lib/fleet.sh on the brain, lib/device.sh on a device, the device
routes in lib/app/server.py), commands, and pinned dispatch (below). Nothing places work on a
device by itself yet.

```
 device (mini)                                          brain (the desk): its app server
 chartroom device run (a LaunchAgent in the login       POST /api/v1/device/join       a one-time code
   session, dev.chartroom.device)                       POST /api/v1/device/heartbeat  every 15 s
   every 15 s: its probe (lib/nodeprobe.sh) ──HTTPS──▶  POST /api/v1/device/rotate     a new token
                                    (Tailscale Serve)   devices/<id>.json, <id>.seen.json
```

- **Enrolling.** On the brain, `chartroom node add --name mini` prints a code: single use, 10 minutes,
  only its sha256 is stored. On the device, after `install.sh --device` (no home is made there),
  `chartroom device join <brain-url> <code>`. The device sends its node id (`CHARTROOM_NODE_ID`,
  minted once by `node init` and kept across `--force`), host name and hardware id; the brain
  answers with a token of 32 random bytes and keeps only its sha256. A second entry for the same
  hardware is refused, naming the first; `node add --replace <name|id>` makes a code that replaces
  it (the old entry is revoked, its name carried over).
- **Where the token lives.** On macOS, `join` writes the code to a 0600 file and loads the agent;
  the agent makes the join itself, in the login session, so the token goes into the login
  keychain (an ssh session often cannot open it): service `chartroom-device`, account the node id.
  Where there is no keychain (Linux, `CHARTROOM_KEYCHAIN=none`) it is a 0600 file. It is sent only
  as a header through curl's config on stdin, never on a command line, and never logged.
- **Its scope.** The device routes open by a device token alone, and only that device's own; the
  Tailscale login is ignored there (every device carries the owner's). A device token opens no app
  route. Ten wrong codes in a minute close the join route for the rest of it.
- **Revoke, rotate, rename.** `node revoke` drops the hash: the device's next request gets 401, its
  agent logs it and stops (exit 0, so launchd's `KeepAlive: SuccessfulExit=false` leaves it
  stopped) and nothing else there is touched. `node rotate` asks for a new token in the next
  heartbeat's answer: the device makes one and sends it, and the old one stays good for 10 minutes
  in case the answer is lost. Names are display only (`node rename`; the old one stays an alias).
- **What the brain makes of the silence.** Decided at read time in lib/fleet.sh, never in the
  server: `online` (heard within 45 s), `stale` (longer; shown with what it last said), `lost` (10
  minutes of the endpoint's own uptime), `new`, `revoked`, `unknown` (the app server is not
  running). The server records when it started (`fleet/endpoint`); a device's silence while it was
  down is not counted, and after a restart every device is `stale` until it speaks.
- **Fleet and `chartroom nodes`.** A device's row is its last heartbeat, read from disk: nothing is
  sent to it. A machine in `CHARTROOM_NODES` whose label is an enrolled device's name or alias is
  not probed over ssh as well; `chartroom nodes --ssh` reads the ssh list alone, as before.
- **Leaving.** `chartroom device leave` stops the agent and deletes the token there; revoke it on
  the brain too.

### Pinned dispatch (built)

- **Pinning.** `new --node <device>` or `set <id> node=<device>|here`, before dispatch, makes the
  task's backend `node:<agent>`. The device's id is in `meta.node`, and what runs there (hc:claude
  or hc:codex) is in `meta.node_backend`. A pin needs a device whose agent says it can take work
  (the `dispatch` capability in its heartbeat).
- **The runner.** `lib/backends/node.sh` is a runner like the others. Launch, steer, stop, peek and
  close each become a command for the device (`fleet/queue/<id>/`), taken by its long-poll.
- **On the device.** `lib/guest.sh` runs them in a guest home,
  `$XDG_STATE_HOME/chartroom/node/guests/<home>/`. That is an ordinary chartroom home of the
  device's own: `new --id` with the brain's brief (its home's paths moved there), then `dispatch`.
  A dispatch sent twice finds the task and starts nothing.
- **What comes back.** The agent's loop pushes the guest log's lines from the dispatch on. The
  brain appends each one verbatim, by offset (`meta.node_off`), so a replay never doubles one.
  report.md, plan.md and new permission cards come back the same way. An answer given on the
  brain is sent back as `permit-sync`.
- **Liveness.** The heartbeat carries each pinned task's live word, and the brain's `status` reads
  it from there.
- **Close.** In this order, stopping at the first step that does not hold:
  1. The device bundles the branch.
  2. The brain fetches it, fast-forward only, into the task's branch.
  3. The brain's tip must equal the device's.
  4. The device closes its guest task and deletes its copy of the branch.
  5. The brain closes the record, and its branch then follows the landed rule.
- **Scope.** A push is taken only for a task pinned to that device at that attempt
  (`fleet/tasks/<home>/<id>.json`), checked by the server and again by `fleet ingest`. A pushed
  line that only the brain writes (an accept, a close) is dropped. Only `report.md` and `plan.md`
  are taken as files. Only cards are taken from a device, never answers.
- **Not yet:**
  - live screen watching;
  - the brain's screen-based stuck checks for a remote worker (turn ends and hook prompts do
    arrive as events);
  - the 4-hour reminder for a pin whose device stays away;
  - automatic placement;
  - handoff.
